# Error Handling Documentation

## Overview

This project implements a standardized error handling system using the `AppError` utility. This system provides consistent error handling across the entire application, with proper type safety and centralized error management.

## Core Components

### 1. AppErrorCode Enum
The `AppErrorCode` enum defines standardized error codes used throughout the application:

- **Authentication errors**: `AUTH_LOGIN_FAILED`, `AUTH_REFRESH_FAILED`, `AUTH_FORBIDDEN`, `AUTH_UNAUTHORIZED`, `AUTH_TOKEN_EXPIRED`
- **Network errors**: `NETWORK_ERROR`, `REQUEST_TIMEOUT`, `REQUEST_ERROR`
- **Generic errors**: `UNEXPECTED_ERROR`, `VALIDATION_ERROR`
- **API specific errors**: `API_ERROR`, `RATE_LIMIT_EXCEEDED`

### 2. AppError Interface
The `AppError` type defines the standard error structure:
```typescript
interface AppError {
  code: AppErrorCode;
  message: string;
  details?: unknown;
  originalError?: unknown;
}
```

### 3. Core Functions

#### `createAppError(code, message, details?, originalError?)`
Creates a standardized application error with the specified parameters.

#### `isAppError(error)`
Type guard to check if an error is an `AppError`.

#### `isAxiosError(error)`
Wrapper around `axios.isAxiosError` that provides type narrowing to `AxiousErrorLike`.

#### `transformError(error, defaultCode?)`
Transforms various error types (Axios errors, standard errors, etc.) to the standardized `AppError` format.

## Usage Patterns

### In Components
```typescript
import { transformError, AppErrorCode, isAppError, isAxiosError } from "@/errors/AppError";

try {
  // Some operation
  await someApiCall();
} catch (error) {
  const appError = transformError(error, AppErrorCode.API_ERROR);
  
  if (isAppError(error) && error.code === AppErrorCode.AUTH_FORBIDDEN) {
    setError(error.message);
  } else if (isAxiosError(error) && error?.response?.data) {
    // Safely extract message from response data
    const responseData = error.response.data;
    if (
      typeof responseData === 'object' && 
      responseData !== null && 
      'message' in responseData
    ) {
      setError((responseData as { message?: string }).message || "Request failed");
    }
  } else {
    setError("An unexpected error occurred");
  }
  
  throw appError;
}
```

### In Services/Libraries
The error transformation should be done at the boundary of external calls, such as in API clients or data fetching functions.

## Integration Points

### Axios Interceptors
The axios instance uses interceptors that transform errors to the standardized format and handle common cases like 401 Unauthorized, 403 Forbidden, and 429 Rate Limiting.

### Server Actions
Server actions in `lib/axios/actions.ts` use `transformError` to return user-friendly error messages.

### Middleware
Authentication and authorization middleware properly handle and log errors using the standardized approach.

### React Query Integration
API hooks generated by Orval maintain compatibility with the error handling system.

## Best Practices

1. **Always use `transformError`** when catching errors from external sources
2. **Use appropriate error codes** from the `AppErrorCode` enum
3. **Handle errors at the right level** - close to where user feedback is needed
4. **Don't over-catch** - let errors bubble up when appropriate
5. **Log errors appropriately** for debugging without exposing sensitive information
6. **Provide user-friendly messages** that help users understand what went wrong

## Error Flow

```
External Error (Axios, API, etc.)
        ↓
   transformError()
        ↓
    AppError Format
        ↓
    Component/Layer
        ↓
   User Feedback
```

## Common Scenarios

### Rate Limiting (429)
- Automatically handled with exponential backoff
- Safe parsing of retry-after headers (1-60 seconds range)

### Authentication Failure (401/403)
- Redirects to appropriate pages
- Clears user session if needed

### Network Errors
- Proper error messaging for offline scenarios
- Graceful degradation

### Validation Errors
- Form validation handled by react-hook-form
- API validation errors transformed to user-friendly messages

## Testing Considerations

Error handling should be tested by:
- Mocking external API calls to return different error types
- Verifying proper error codes are returned
- Checking that appropriate user feedback is provided
- Confirming that errors are logged correctly
